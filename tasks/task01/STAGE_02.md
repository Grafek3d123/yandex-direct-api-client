Продолжай работу с существующим репозиторием `yandex-direct-api-client`.

Этап 1 должен быть завершён.

Сейчас реализуй основной набор ресурсов Yandex Direct API поверх архитектуры, подготовленной на первом этапе.

## Цель

Создать удобный и типизированный интерфейс для работы с основными объектами Yandex Direct.

Не реализуй:

* MCP;
* AI;
* автоматическую оптимизацию;
* генерацию рекламных текстов;
* маркетинговую бизнес-логику.

Клиент только предоставляет API.

## Ресурсы

Рассмотри и по необходимости реализуй:

* кампании;
* группы объявлений;
* объявления;
* ключевые фразы;
* минус-фразы;
* ставки;
* стратегии;
* регионы/географию;
* расписание показов;
* метки;
* дополнительные элементы объявлений;
* быстрые ссылки / sitelinks;
* другие близкие сущности, необходимые для нормальной работы с рекламными кампаниями.

Не пытайся реализовать редкие возможности только ради количества.

Для каждого ресурса определи реально полезные операции:

* list;
* get;
* create;
* update;
* delete;

только там, где соответствующая операция поддерживается официальным API.

## Модели

Используй типизированные модели.

Не заставляй пользователя постоянно работать с raw JSON.

Например:

```python
campaign.id
campaign.name
campaign.state
```

Модели должны корректно отражать:

* вложенные структуры;
* optional-поля;
* enum-подобные значения;
* списки;
* связанные сущности.

Не создавай избыточное количество классов без необходимости.

## Request / Response

Разделяй:

* параметры запроса;
* модели ответа;
* HTTP internals;
* публичный API библиотеки.

Но избегай искусственного усложнения.

## Безопасность

Все операции изменения должны использовать единый механизм:

* `readonly`;
* подтверждение опасных операций;
* массовые изменения;
* понятные ошибки.

Удаление и опасные bulk-операции не должны выполняться случайно.

## Batch и ограничения API

Учитывай реальные ограничения Yandex Direct API:

* количество объектов в запросе;
* chunking;
* batching;
* rate limits;
* повторные запросы;
* частичные ошибки.

Ограничения сверяй с официальной документацией.

Не дублируй одну и ту же batching-логику в каждом ресурсе.

## Ошибки

Ошибки API должны преобразовываться в понятные исключения библиотеки.

Проверь обработку:

* 400;
* 401;
* 403;
* 404, если применимо;
* 409, если применимо;
* 429;
* 500+;
* ошибок уровня Yandex Direct API.

Не теряй полезную информацию из ответа API.

## Обратная совместимость

Старые методы можно менять.

Но если старый и новый API решают одну и ту же задачу, не создавай две независимые реализации.

Лучше один основной путь выполнения плюс совместимый внешний интерфейс, если он нужен.

## Тестирование

Для каждого основного ресурса добавь тесты на:

* успешное чтение;
* создание;
* изменение;
* удаление;
* ошибки;
* readonly;
* confirmation;
* batching;
* вложенные модели.

Тесты не должны требовать реального рекламного кабинета.

## Обязательный отчёт

Этот этап должен иметь **ровно один отчёт**.

Если задание сохранено как:

```text

```

```text

```

Не создавай отчёты для отдельных исходников.

То есть НЕ создавай:

```text

models_report.md
test_ads_report.md
```

Нужен только:

```text

```
