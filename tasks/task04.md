## 0. Бизнес-контекст (для привязки acceptance-критериев, не для кодирования)

Первый реальный сценарий использования SDK:
- мужские печатки и перстни, изготовление из золота заказчика, изготовление по эскизу;
- география: вся РФ, кроме Москвы, МО, Санкт-Петербурга, Ленобласти;
- Яндекс Метрика уже установлена → нужна привязка счётчика и цели;
- старт — минимальная осторожная открутка; через ~2 недели — анализ и корректировка;
- ориентир по бюджету: 20 000 ₽/мес.

**Ограничения этого блока:**
- 20 000 ₽/мес — бизнес-константа проекта, **не дефолт и не ограничение SDK** (зашивать в код нельзя);
- перечисленные 4 региона — конфигурация конкретной кампании, **не зашивается в SDK** как бизнес-правило;
- автоматическое создание реальной рекламной кампании бизнеса этим этапом **не выполняется** — только
  безопасная техническая возможность + live smoke на тестовых сущностях;
- задача этапа — дать SDK возможность безопасно создать/управлять такой кампанией, а не покрыть 100% API.

## 2. Слой 0 — Фундамент

### F-0.1. Версионирование API в едином транспорте (нужно для 2Б)

- Транспорт должен принимать версию API для конкретного вызова: `post(service, payload, *, api_version="v5")`.
- URL строится как `{api_url}/{api_version}/{service}/`; `api_url` остаётся настраиваемым (песочница, прод).
- По умолчанию `v5` — все существующие сервисы работают как раньше.
- ЕПК-операции используют `v501`; отдельный HTTP-клиент для v501 **не создаётся**.
- Внутренний API версии не должен протекать в публичные методы сервисов наружу (кроме явного low-level хелпера).

**AC:** `post(..., api_version="v501")` строит `.../json/v501/campaigns/`; дефолтный путь `.../json/v5/campaigns/`; все существующие тесты проходят без правок.

### F-0.2. Необязательный `client_login` (D4)

- `token` — обязателен; `client_login` — необязателен.
- Если передан — заголовок `Client-Login` присутствует; если не передан — заголовок не добавляется.
- Агентский сценарий (обход клиентов) не ломается: `client_login` на экземпляр по-прежнему работает.
- `readonly`/`confirm`-гарантии не меняются.

**AC:** 3 теста — прямой рекламодатель без `client_login`; с `client_login`; агентский сценарий. Регресс: все текущие тесты на `Client-Login` зелёные.

### F-0.3. Единый модуль лимитов API

- Вынести в `services/_base.py` (или `limits.py`) константы: `CAMPAIGNS_ADD_MAX=10`, `MUTATE_MAX=200`, `GET_IDS_MAX=1000`, `GET_PAGE_MAX=10000`, `ADGROUPS_GET_MAX=10000`.
- Применить ко всем сервисам; убрать хардкод `10000` из `services/ad_groups.py`.
- `campaigns.create_many()` с чанкингом по 10.

**AC:** 15 кампаний → 2 вызова (10 + 5); 2500 `suspend` → 3 вызова; 201 группа → 2 вызова; 2500 ID в `get` → корректный чанкинг.

### F-0.4. Классификация ошибок и `request_id`

- `ApiError` дополнить: `is_retryable`, `is_fatal`, `is_validation`, `retry_after`, `request_id` (из заголовка `X-Request-Id`), идентификатор объекта (`campaign_id`/`ad_group_id`/`ad_id`).
- Классы: retryable (429, 5xx, временные коды), auth (401/403, нет доступа к клиенту — без повторов), validation (бизнес-ошибки тела), fatal (лимит объектов, нет прав, блокировка).
- `retry.py`: не повторять auth/validation/fatal; повторять только retryable, с учётом `Retry-After`.

**AC:** 401 → `AuthError` и **ноль** повторов; 429 × N → `RateLimitError` с `retry_after`; код лимита объектов → `ApiError(is_fatal=True)` без повторов; `request_id` присутствует в исключении и в логе.

### F-0.5. Частичные результаты batch-операций

- Параметр `on_item_error: Literal["raise", "collect"]`, default `"raise"` (BC не ломается).
- В `"collect"` возвращается `BatchResult(succeeded=[...], failed=[ItemFailure])`; `ItemFailure` несёт `id`, `message`, `code`, `request_id`.
- `check_item_errors` → `partition_results(results, result_key)`; все сервисы переводятся на неё.

**AC:** ответ 3 успеха + 1 ошибка в `"collect"` → `succeeded=3`, `failed=1`, исключения нет; в `"raise"` поведение как сейчас.

### F-0.6. Структурированное логирование + redactor

- `logging.py` c `NullHandler`; `extra`-поля: `service`, `api_version`, `method`, `client_login`, `request_id`, `status_code`, `duration_ms`, `attempt`, `readonly`.
- Уровни: DEBUG — тела payload/ответ (только при `YANDEX_DIRECT_LOG_BODIES=1`), INFO — успешные мутации (id, имя, бюджет), WARNING — retry/частичные ошибки, ERROR — терминальные.
- Redactor маскирует `Authorization`, `token`, `access_token`, `refresh_token`, `password`; применяется к логам, `repr` исключений и `response_body`.

**AC:** по умолчанию клиент ничего не печатает; токеноподобная строка в `error.details` отсутствует в `str(exc)` и в логах; каждый лог-вызов содержит `request_id`.

### F-0.7. Пред-отправочная валидация

- `validation.py`: структурная (whitelist обязательных полей, отбрасывание `None`), бизнес-валидация (лимиты символов, URL, положительность бюджета/ставки, `end_date > start_date`, непустой `RegionIds`, допустимость `Type`), кросс-сущностная (`campaign_id`/`ad_group_id` существуют, `region_ids` ⊂ справочника).
- Режимы: `validate=True` (default) / `validate=False` (escape-hatch). Флаг в `Settings`.

**AC:** ≥ 30 негативных кейсов → `ValidationError` и **0 HTTP-вызовов**; `validate=False` отправляет как есть; текущие тесты не падают.

### F-1.2. `RegionSelector` — общий механизм гео (D5)

- Никаких бизнес-значений в SDK: ни «вся РФ», ни «исключить МСК/СПб/ЛО/МО» как зашитых констант.
- API: `RegionSelector(include=[...], exclude=[...])`, где каждый элемент — `RegionId(int) | "код" | "название"`.
- Резолв названий и кодов — только через `client.dictionaries().geo_regions()`; **выдуманные ID запрещены** — при неизвестном значении `ValidationError` с ближайшими совпадениями.
- Методы: `.include_all_russia()`, `.resolve(dictionaries) -> List[int]`, `.current(ad_group) -> List[int]` (прочитать текущие регионы).
- Неоднозначность («Тверская» = город или область) → `ValidationError` с требованием уточнить, а не молчаливый выбор.
- Пустой результат резолва → `ValidationError` (не отправлять `RegionIds: []`).

**AC:** `RegionSelector(exclude=["Москва","Московская область","Санкт-Петербург","Ленинградская область"]).resolve(...)` → ≥ 75 ID, ни один не содержит ID исключаемых регионов (сверка с golden-фикстурой); неизвестный регион → `ValidationError` + подсказки; неоднозначное название → `ValidationError`; повторный `resolve` — 0 HTTP-вызовов (кэш).

## 5. Слой 2Б — ЕПК / Unified Campaign + Responsive Ads (v501) — **в объёме (D1)**

### F-2B.1. Модель `UnifiedCampaign`

- Отдельный typed-модельный слой (не смешивать с `TextCampaign` в одном неуправляемом классе).
- Поля: `name`, `start_date`, `end_date` (опц.), `currency`, `strategy`, `regions`, `counter_ids`, `priority_goals`, unified-specific настройки, `raw` для неизвестных полей.
- `to_add_payload()` / `to_update_payload()` (у update — `Id` + изменяемые поля).
- Существующая `Campaign` остаётся общей моделью **ответа** и расширяется без breaking change.

### F-2B.2. `ResponsiveAd`

- Typed-модель: несколько заголовков, несколько текстов, `href`, изображения, `video` (если поддерживается), `business/contact information` (только если нужно сценарию), `tracking params`, `raw` для остальных полей API.
- **Не удалять** поддержку `TextAd`.
- `client.ads.create_responsive(...)` — SDK сам собирает корректный payload; ручной `{"AdType": ...}` пользователю не нужен, но raw/advanced payload остаётся как расширение.

### F-2B.3. Метрика: счётчик и цели

- Поля ЕПК `CounterIds` и `PriorityGoals` — типизированные.
- Разделены сущности: `counter_id`, `goal_id`, `goal_name` (только для отображения), `goal_priority`.
- **Хранить цели по ID, не по названиям.** SDK не выбирает цели за пользователя.
- Полноценное управление Метрикой в объём **не** входит (это задача отдельного клиента Метрики).

### F-2B.4. Гео ЕПК

- Реализовать «добавить регионы / исключить регионы / прочитать текущие» через тот же `RegionSelector` (F-1.2), что и для v5 — без дублирования логики.
- Структуру запроса ЕПК-группы сверить с документацией; **не переносить поля `TextCampaign` автоматически**.

### F-2B.5. Стратегия и бюджет ЕПК

- Поля стратегии, недельный бюджет, ограничение ставки (если поддерживается стратегией), прочие обязательные поля конкретной стратегии.
- SDK **не выбирает стратегию за пользователя** и **не подставляет «оптимальный» бюджет**.
- Хелпер преобразования `monthly → weekly` допустим, но фактическое отправляемое значение должно быть видно пользователю.
- 20 000 ₽/мес в код не зашивается.

### F-2B.6. `CampaignService` для ЕПК

Расширить существующий сервис (без дублирования HTTP-клиента): `create_unified`, `get_unified`, `update_unified`, `delete_unified`, `suspend`, `resume`, `archive`, `unarchive` — с маршрутизацией на v501 там, где этого требует ЕПК. Существующие методы для старых кампаний не ломаются.

**AC слоя 2Б:** unit-тесты сериализации `UnifiedCampaign` (add/update), `ResponsiveAd` и его валидации, `CounterIds`, `PriorityGoals`, стратегии, бюджета; выбора версии v5/v501; создание ЕПК → группы → `ResponsiveAd` в live smoke; `readonly`/`confirm` работают на всех новых методах.

## 6. Слой 3 — Ставки и бюджеты (D6, D7)

### F-3.1. Типизация денег
- `to_money_units` / `from_money_units`, `Decimal`, округление по правилам API; константы множителя — в `config.py`.

### F-3.2. Стратегии
- `models/bid_strategy.py`: набор стратегий (ручная CPC/CPM, без ограничения средней цены, оптимизация по конверсиям/целям ЕПК и т. п. — состав по D7).
- Каждая: `to_payload()` + `from_dict()`; `campaigns.get` читает соответствующие секции.
- Escape-hatch: `dict` для редких/новых полей стратегии, с пометкой в docstring.

### F-3.3. Операции над бюджетом
- `set_weekly_budget(ids, budget, *, verify=True)`, `set_daily_budget(ids, budget, *, verify=True)` (применимость зависит от типа кампании/стратегии), `get_budgets(ids)`, `set_bid_strategy(ids, strategy, *, verify=True)`.
- `verify=True` (default) — после update делает `get` и сверяет; при расхождении `ApiError` с обоими значениями.
- Хелпер `monthly_to_weekly(amount)` — без сокрытия фактического значения.
- `set_bid`/`set_bids` — валидация диапазона, поддержка `bid_type`.

### F-3.4. Предохранители бюджета
- `daily_budget_cap: Optional[Decimal]` (env `YANDEX_DIRECT_BUDGET_CAP`): превышение → `ValidationError` **до** сети. Это защита от «залил случайно», а не дефолт и не бизнес-константа.
- `require_confirm_for_money: bool` (default `True`): денежные мутации требуют `confirm=True`.

**AC:** `set_weekly_budget(ids, 5000.0)` → в теле API точное значение в единицах ×1 000 000; `verify=True` → 2 вызова, значения совпали; превышение cap → `ValidationError` и 0 вызовов; `readonly=True` → `ValidationError`; round-trip тест `to_payload → from_dict` для каждой стратегии.

## 8. Слой 5 — E2E-сборка запуска (в `scripts/`, не в пакете)

> **Граница (решение владельца):** пакет остаётся набором атомарных операций Direct-капити —
> оркестрация запуска не попадает в `yandex_direct_api_client/`. Сборка живёт в `scripts/` и
> использует только публичный API клиента. Соответственно, AC «dry_run → 0 вызовов» проверяется
> unit-тестом, который импортирует модуль скрипта, а не тестом пакета.

- Скрипты `scripts/launch_rsy.py` (сценарий 2А) и/или `scripts/launch_epk.py` (сценарий 2Б):
  `launch(client, spec, *, dry_run=False, poll_interval=30, poll_timeout=3600, confirm=False) -> LaunchResult`.
- Последовательность: справочники → гео-резолв → кампания → группа → креатив(ы) → объявление(я) → `moderate` → `resume` (если нужно) → опциональный поллинг статуса.
- `dry_run=True` — только валидация и план, **ноль** сетевых вызовов.
- Компенсация: `LaunchResult.partial_ids` + `rollback(..., confirm=True)` (архив созданного) при сбое на шаге ≥ 2.
- **Автоматическое создание реальной кампании бизнеса не выполняется** — только техническая возможность и тестовые сущности.

**AC:** `dry_run=True` → 0 вызовов; happy-path до `MODERATION`; сбой на `ads.create` → `partial_ids` и рабочий `rollback`; повторный запуск с тем же креативом не грузит его второй раз (кэш по хэшу содержимого).

## 9. Слой 6 — Тестирование

### 9.1. Правила (AGENTS.md §5)
- `tests/` — **только mock HTTP** через `responses`. Никаких сетевых вызовов в обычном `pytest`.
- Реальные запросы — **только** в `scripts/`, вручную, вне прогона `pytest`. Секреты из `.env`.
- Каждый новый публичный метод `YandexDirectClient` имеет unit-тест. Существующие тесты не удаляются.

### 9.2. Уровни
| Уровень | Назначение | Инструмент |
|---|---|---|
| L1 Unit | билдеры payload, резолверы, валидаторы, деньги, версия API | чистый Python |
| L2 Contract | точный JSON-тело каждого метода, коды ошибок, retry, частичные batch | `responses` |
| L3 Live | полный жизненный цикл на прод-клиенте, всё в `DRAFT` | `scripts/smoke_*.py`, вручную (D9) |
| L4 Live read-only | смоук существующих кампаний | `scripts/check_api.py` (по образцу) |

### 9.3. L2 — обязательные сценарии

Фундамент: F-0.1 (v5/v501 URL), F-0.2 (3 сценария `Client-Login`), F-0.3 (чанкинг 15/2500/201), F-0.4 (401/429/лимит объектов), F-0.5 (3 успеха + 1 ошибка), F-0.6 (утечка токена), F-0.7 (≥ 30 негативных payload'ов), G16 (параметризованный `readonly` по всем мутирующим методам).

Справочники/гео: `geo_regions("RUC")` ≥ 80; кэш без сети; `RegionSelector.resolve` без 4 регионов; неизвестный регион; неоднозначное название; `can_create_campaign`.

РСЯ (2А): snapshot тела `CpmBannerCampaign`; `BannerAdGroup` c `Type`; `region_ids=[0]` → ошибка; `create_rsya_banner` тело; креатив невалидного формата → 0 вызовов; `moderate` для не-`DRAFT`.

ЕПК (2Б): сериализация `UnifiedCampaign` add/update; `ResponsiveAd` (заголовки/тексты/изображения) + валидация; `CounterIds`; `PriorityGoals`; стратегия; недельный бюджет; `create_unified` маршрутизируется на v501; v5-методы остаются на v5.

Общее: `set_weekly_budget` + `verify`; превышение cap; отчёты по кампании (`Cpm`, `Impressions`, `Ctr`); `dry_run` → 0 вызовов; сбой → `partial_ids` + `rollback`.

### 9.4. L3 — live-скрипты (в `scripts/`, вручную)

- `scripts/smoke_campaign_live.py` — общий permanent-скрипт с флагом `--scenario S-0X` (по образцу существующих `scripts/`).
- Проверки: авторизация → создание (РСЯ **и** ЕПК — по D1) → группа → креатив/объявление → чтение → ключевые поля → регионы → стратегия/бюджет → связка campaign/group/ad → удаление → cleanup **даже при ошибке**.
- Вывод: `RequestId`, созданные ID, этап ошибки, результат cleanup. **OAuth-токен не выводится никогда.**
- Тестовые имена вида `SDK Smoke Test YYYYMMDDHHMMSS`; **реальные данные бизнеса не используются**; реальные `CampaignId`/`CounterId` в репозиторий не попадают.
- **Контур (D9):** реальный клиент, все объекты остаются в `DRAFT`, показы не запускаются
  (`Network = SERVING_OFF` либо `suspend` в финале), самоочистка в `finally`, ненулевой код возврата
  при провале. Реальные креды владелец предоставляет на финальном этапе — до этого L3 не запускается
  и в отчёте помечается «ожидает прогона».
- **Гео-проверка:** сценарий с `RegionIds` = 5 регионов РФ вне МСК/СПб/ЛО/МО (Тверская, Омская, Краснодарская, Иркутская, Калининградская) и сценарий «вся РФ кроме четырёх» — **прямая проверка исходного вопроса бизнеса об отсутствии региональных ограничений**.

### 9.5. Качество
- `pytest`, `ruff check .`, `mypy yandex_direct_api_client` — зелёные; новые модули покрыты ≥ 90% строк mock-тестами.
- Python 3.9 совместимость (никаких `X | Y` в рантайме).
- Регрессия существующих 160 тестов — обязательна (базовый прогон: `160 passed`).

## 14. Приложение. Ответ на исходный вопрос бизнеса

**Можно ли создать кампанию с показом в РСЯ по РФ, кроме Москвы, МО, Санкт-Петербурга и Ленобласти?**

**Да, ограничений по географии в Yandex Direct API нет.** Регионы задаются списком ID; отдельного механизма
«исключить гео» в API не существует — исключение реализуется перечислением всех нужных регионов.
Возможны оба пути: классическая CPM-кампания (`v5`) и ЕПК (`v501`) — ограничений по регионам нет у обоих.
ID регионов берутся из `dictionaries/getGeoRegions`; в SDK это закрыто механизмом `RegionSelector` (F-1.2),
который умеет принимать ID, коды и названия регионов и сам подтягивает справочник.

Фактические ограничения, не связанные с географией: доступ к Direct API для OAuth-приложения, права на клиента
(прямой доступ или агентство), лимит кампаний клиента, наличие валидного креатива, привязка цели Метрики для
стратегий с оптимизацией по конверсиям.

### Б.2. Риск для автоматизации и запасной план (D11)

**Проблема.** Классическая РСЯ (`CPM_BANNER_CAMPAIGN`) требует креатив, который API создать не может.
Полностью автоматизировать «картинка → объявление РСЯ» для `CPM_BANNER_CAMPAIGN` нельзя: последний шаг
требует ручного действия в веб-интерфейсе (конструктор креативов) и передачи `CreativeId` в SDK.

**Запасной план (план Б, обязателен к реализации): полная автоматизация через ЕПК.**

Сценарий ЕПК закрывает ту же задачу «баннер с картинками» целиком через API:

1. `adimages.add` / `add_from_file` / `add_from_stream` → получаем `AdImageHash` (картинка загружена нами);
2. `campaigns.create_unified` (v501) → ЕПК-кампания с недельным бюджетом и стратегией;
3. `ad_groups.create([UnifiedAdGroup(...)])` → группа ЕПК с `RegionIds` (тот же `RegionSelector`);
4. `ads.create_responsive_ad(..., ad_image_hashes=[hash])` → комбинаторное объявление с картинками;
5. `moderate`/`resume` → показы.

То есть ЕПК — не «запасной вариант», а основной путь автозапуска; классическая CPM-РСЯ остаётся для
ручных/специфичных сценариев, где креатив уже создан в веб-интерфейсе (его `CreativeId` читается
`client.creatives.image_creative_ids()`).

**Что из этого обязательно к проверке на live-этапе 8:**

- ЕПК-сценарий целиком (загрузка картинки → объявление с картинкой) без ручных шагов;
- классический CPM-сценарий — с креативом из `creatives/get`; если у клиента нет готовых креативов,
  фиксируется в отчёте как ограничение, а не как баг SDK.
